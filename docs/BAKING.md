## 店主的規範（原文）

# 3D 場景優化與貼圖烘焙管線規範 (Blender to Three.js / glTF)

> ⚠️ **【核心適用範圍聲明：僅限靜態物件 (STATIC OBJECTS ONLY)】**
> 本規範之所有烘焙（Baking）、網格合併（Mesh Merging）與圖集打包（Texture Atlas）流程，**嚴格僅適用於場景中「完全不會移動、旋轉、縮放或被玩家拾取互動」的靜態環境物件**（如：建築牆體、地板、天花板、固定吧台、固定門框、不可移動的大型裝飾）。
> * **嚴禁套用於**：動態互動道具（可拿取的餐具、食材）、可移動家具（椅子）、NPC 角色、物理碰撞剛體，以及大量重複的標準化小物（應改用 Three.js `InstancedMesh`）。

---

## 一、 物件分類與處理決策樹

在執行任何 Blender Python 生成或匯出腳本前，必須先將場景物件分為以下三類，嚴格隔離處理：

| 物件類別 | 判定標準 | 允許執行之優化手段 | 禁止事項 |
| :--- | :--- | :--- | :--- |
| **1. 純靜態建築與大型陳設**<br>*(Static Environment)* | 座標永久固定、無物理動態、無獨立互動邏輯 | **完整執行【階段 A + 階段 B】**<br>（高轉低模 + 場景光影/AO烘焙 + UV圖集打包 + 合併網格） | 禁止保留未合併的零碎子網格導致 Draw Call 飆升 |
| **2. 動態與可互動道具**<br>*(Dynamic / Interactive)* | 玩家可拾取、移動、觸發動畫或需獨立碰撞體 | **僅執行【階段 A】**<br>（單件高轉低模 + 獨立 Normal/ORM 貼圖） | **嚴禁執行【階段 B】**<br>不可烘焙進場景地板陰影、不可與其他物件合併 (`Ctrl+J`) |
| **3. 高重複性標準物件**<br>*(Instanced Props)* | 場景中出現 $\ge 5$ 個相同幾何體（如盤子、磁磚、燈籠） | **僅執行【階段 A】**，匯出單一原型 `.glb` | 不可在 Blender 內直接合併成單一巨大 Mesh，交由前端 Three.js `InstancedMesh` 渲染 |

---

## 二、 靜態物件標準執行管線（階段 A + 階段 B 串聯）

針對符合條件的**靜態物件**，自動化腳本必須依序執行以下兩階段：

### 階段 A：單件減面與細節轉印 (High-to-Low Poly Bake)
1. **建立低模 (Low-Poly)**：對高細節模型複製並簡化拓撲（Decimate / Retopology），確保三角形面數符合網頁效能標準，同時保持剪影輪廓完整。
2. **轉印法線與遮蔽**：使用 `Selected to Active` 烘焙模式，將高模表面凹凸與縫隙轉印至低模的 **Normal Map** 與 **Ambient Occlusion (AO)**。
3. **清理高模**：烘焙完成並確認貼圖寫入後，立即刪除或排除高模（High-Poly），確保不進入最終匯出列表。

### 階段 B：靜態群組圖集打包與光影烘焙 (Texture Atlas & Light Bake)
1. **空間分群 (Spatial Grouping)**：依視線遮擋關係（Occlusion）將靜態物件劃分為 2～4 個區域群組（例如：`外場用餐區`、`吧台料理區`、`建築主結構`），避免將全場景塞入單一貼圖導致解析度不足。
2. **非重疊 UV 重排**：為群組內所有靜態低模建立第二組 UV（或重排主 UV），執行 `Pack Islands`（設定適當 Margin 避免滲色），確保所有物件互不重疊地分配在同一張 `2048x2048` 或 `4096x4096` 貼圖空間內。
3. **靜態光影與材質烘焙**：
   * 優先採用 **Combined (Full Render)** 烘焙（將基礎色、環境光遮蔽 AO、靜態燈光投影直接算入單張貼圖），使網頁端可使用無光照材質（`MeshBasicMaterial`）達到最高 FPS。
   * 若該靜態群組仍需保留局部即時反光，則分開烘焙 **Base Color**、**Normal** 與 **ORM 通道打包圖**（`R=AO`, `G=Roughness`, `B=Metallic`）。
4. **網格合併 (Mesh Join)**：確認所有貼圖節點已正確重新對應至打包後的 UV 圖集，將該群組內的所有靜態低模合併（`bpy.ops.object.join()`）為單一 Mesh，使該區域在 Three.js 中的 **Draw Call 降為 1**。

## 三、 glTF / `.glb` 匯出強制檢查清單 (Claude 執行規範)

每次撰寫 Blender Python 腳本執行匯出時，必須自動驗證以下條件：

* [ ] **貼圖格式合規**：嚴禁在最終匯出材質中保留純 `Bump` 節點，所有凹凸效果皆已烘焙轉換為標準 `Normal Map`（OpenGL 格式，Non-Color 色彩空間）。
* [ ] **貼圖尺寸與壓縮**：貼圖解析度必須為 2 的次方（`1024` / `2048` / `4096`），並啟用 KTX2 / BasisU 或 Draco 幾何壓縮以控制載入體積。
* [ ] **動態物件隔離確認**：已確認任何帶有 `interactive_`、`dynamic_` 或 `prop_instanced_` 前綴的物件，均**未被納入**靜態圖集烘焙與網格合併腳本中。
* [ ] **法線與變換套用**：匯出前已對合併後的靜態 Mesh 執行 `Apply All Transforms`（套用位置、旋轉、縮放）並確認面法線朝外。

## 照本專案的做法（Claude 補的，2026-11-22）

店主的原文照做，只有下面這幾處依本專案的固定規則與現有的程式調整，理由寫在每一條。

### 一、分類怎麼判斷（本專案的例子）

- **1. 靜態（階段 A＋B）**：遊戲程式不會移動、轉動、縮放、隱藏它，也不會換它的材質或貼圖，而且不靠名字找它（`getObjectByName`、`take(...)`）。例：牆、地板、天花板、樑柱、門框、固定的吧台與台面、櫃子的外殼、牆上的掛飾、神棚本體、神棚板與托架。開發者模式能移動的 `Movable` 也算靜態：那是擺設時的編輯，不是遊戲進行中的移動。
- **2. 動態、可互動（只做階段 A）**：例：會開關的門扇（神棚的門、飲料櫃的門、拉門）、會被拿起的東西（御神酒壺、碗盤、食材、鐵串、炭袋、飲料瓶）、內容會變的東西（酒杯裡的酒、點了會換花的花瓶）、會藏起來的東西（惠比壽在門關著時不畫）、人物、會亮會暗的燈（燈籠的紙、燈泡、招牌燈的發光材質），以及遊戲靠名字去找的節點。
- **3. 重複五個以上（只做階段 A，匯出一個原型）**：前端用 `InstancedMesh` 畫。專案裡已經這樣畫的照舊，新做的照這條做。

### 二、階段 A 在本專案

- 在 `blender/*.py` 裡做。高模只拿來烘，烘完就刪，不進 glb。低模照 `docs/MODELING.md` 與 `CLAUDE.md` 的 Low-Poly 鐵律：小物件 50～100 面、不從中心放射收聚、封口用梯狀。
- 烘焙用 Cycles 的 Selected to Active。法線貼圖是切線空間（OpenGL，+Y），圖設 Non-Color，接 `ShaderNodeNormalMap`。AO 乘進顏色，最暗不低於六成（第 60 項：惠比壽烘到三成五時，胸口出現一條黑帶）。形狀簡單的（例如圓木），用法線算出的凹槽陰影代替 AO：AO 的射線會被低模自己擋住。
- 高模的平滑要先分好：圓柱的端面設成平面。不然烘出來的法線會沿著長邊歪掉（第 573 項：山牆的圓木）。
- 遊戲端：模型的材質在載入時大多換成卡通材質（`MeshToonMaterial`）。法線貼圖要在換材質的地方接上（例：`DiningRoom.tsx` 的 `kamidanaOf` 對 `KamiRoof*`），不然會被丟掉。
- 每件都要近拍前後對照（同一個鏡頭）與線框；看得出變差就改，或退回。例：第 573 項試過給屋面的瓦層加法線貼圖，在卡通光下，原本清楚的瓦層線變淡、斷斷續續，就拿掉了。
- 做過的例子：惠比壽（第 59、552 項）、神棚的山牆（第 573 項 `gable_bake`）、刷卡機的按鍵圖（第 530 項）。

### 三、階段 B 在本專案

- **光影：不烘直接光（不用 Combined、不用無光照的 `MeshBasicMaterial`）**。店內的燈會開關（固定規則 2～4：玄關兩個開關各管一條線路、廁所另有開關、門口燈籠開店時自動點亮），也有晝夜。把開燈時的光影烘死在貼圖上，關燈後畫面就錯了。所以用規範的第二種：分開烘 Base Color（AO 乘進去）與 Normal。材質維持卡通材質，照店內即時的燈光打光，描線照舊。
- **ORM**：本專案的木頭、布、灰泥都是卡通材質，沒有粗糙度與金屬度，所以不用 ORM。金屬（神棚的金件等）是 `MeshPhysicalMaterial`，要反射攝影棚，留在自己的材質，不進圖集。
- **圖集**：同一區的靜態低模，主 UV 重排（或加第二組 UV），打包進一張 2048（區域小就用 1024；長寬可以不同，例如 1024×512），邊距至少 8 px，防止滲色。原本重複鋪的貼圖（木紋、樹皮）先烘進圖集。
- **合併**：本專案每件擺設都是一個 `Movable`，開發者模式要能各自移動、存位置，所以不在 Blender 裡把不同擺設合成一個網格。同一個模型檔裡的靜態零件，照舊在匯出前合併（例：`kamidana.py` 的 `merge_kids`）。「一區一次繪製」靠執行時的合併達成：`StaticBatch`、`mergeByMaterial`，以及全場合併 `scene/WorldBatch.tsx`（`worldMerge.ts`）會照材質把共用同一張圖集的擺設併成一份。所以同一區的靜態擺設要共用同一個材質，也就是同一張圖集。
- **不能進圖集的**：金屬（要反射）、透明或鏤空（`alphaTest`、雙面）、發光（燈籠的紙）、會換貼圖的東西。這些各自一份，數量盡量少。

### 四、匯出檢查在本專案

- **Bump**：`blender/common.py` 的 `pbr` 沒有 Bump 節點。法線貼圖一律用 `image(..., data=True)`（Non-Color）接 `ShaderNodeNormalMap`。
- **2 的次方**：用 512、1024 或 2048。
- **壓縮**：目前貼圖是 WebP（`export_dish`），幾何沒有壓縮。下載量與顯示卡記憶體在第 571 項量（優化視窗）。可選的做法：
  - 幾何用已經裝好的 meshoptimizer（glTF-Transform 的 `meshopt`；drei 的 `useGLTF` 本來就會解）。
  - 或用 Draco（three 附有解碼器，放進 `public/` 就好，不用下載；但編碼器 `draco3d` 只是間接依賴）。
  - KTX2／BasisU 的編碼工具沒裝，要裝得先問店主（下載檔案）。

  第 571 項定了格式後，各區照那個格式壓縮。
- **動態物件隔離**：本專案的節點不用 `interactive_`／`dynamic_`／`prop_instanced_` 前綴：遊戲靠現有的名字找節點，改名會壞（守則：不要順手改名）。改成每個區域的烘焙腳本開頭列出這區的動態節點名單，由腳本自己檢查這些節點沒有進圖集與合併。之後新做的會動零件，名字加 `dynamic_` 前綴。
- **變換與法線**：匯出用 `export_apply`；合併後的網格套用變換；法線朝外（`normals_make_consistent`）。做完跑 `node scripts/mesh-audit.mjs` 與 `node tests/e2e/clips.mjs`。
- **減面工具**：`blender/optimize_glb.py` 只減超過 1,500 面的網格，會把烘好的乾淨低模一起減碎。所以烘好的低模合併時要自成一組（第 573 項）。改一件以後，要量減面之後的整個 glb，不能只量改的那件：同組其他零件可能因為整組掉到 1,500 面以下而不再被減，總數反而變多。

### 五、每一區的流程

1. **盤點**：列出這區每件擺設，各歸到三類中的哪一類。量這區視角的每格繪製次數、三角面（取九格的中位數，像 `tests/e2e/_roofcost573.mjs`），以及模型的面數。
2. **階段 A**：一件一件做，每件都拍同一鏡頭的前後近拍與線框（像 `tests/e2e/_roof573.mjs`：`OLD=` 換回舊模型拍，`WIRE=1` 拍線框）。
3. **階段 B**：做圖集、改遊戲端材質、確認合併；量繪製次數。
4. 前後數字寫進下面的「區域進度」與 `TASKS.md` 第 574 項，提交、推上 main，通知其他視窗動到哪些檔案。
